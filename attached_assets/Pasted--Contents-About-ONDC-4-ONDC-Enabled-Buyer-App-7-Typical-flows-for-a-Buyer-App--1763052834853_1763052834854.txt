CHAPTER 1: Introduction to ONDC
About ONDC
Open Network for Digital Commerce (ONDC) aims to democratize digital commerce by enabling an interoperable framework, for different demand side entities (also called buyer network participant or buyer NP) & supply side entities (also called seller network participant or seller NP) to transact, while providing the convenience and quality of service that is available in digital commerce today.
ONDC participants, on the demand & supply side, define their terms & conditions and dynamically enter into a contractual relationship, by signing a digital contract, to facilitate a transaction between the buyer and seller.
Please refer to the following links for additional information on ONDC:
ONDC Website
ONDC Strategy Paper - The strategy paper briefly explains India’s commerce ecosystem, building digital commerce on an open network, building blocks of ONDC as a network and its implementation
ONDC Consulting Paper - The consulting paper elaborates about ONDC Network architecture, detailed flows for an ONDC enabled transaction determinants of trust in e-commerce, governing laws and trust-building measures conceptualized by ONDC
ONDC technical specifications 
ONDC Resources

CHAPTER 2- Customizing Saarthi
Technology Stack
Saarthi has been developed using React Native for mobile, with a backend powered by Node.js and Python. It provides plug-n-play integration with services for payment, maps, etc. with default out-of-the-box configurations available for Razorpay (payment), Bhashini (language support), email/SMS integration, and Mappls (maps), Odoo (order management).

Follow API integration details as mentioned here

g. Signing and Verification
Rules for Signing and Verification
Ed25519 signing keys (private key of at least 64 bytes, public key of at least 32 bytes)
Libsodium for Signing and Verification

Application Deployment Steps
Salient features of deployment:
All services are run via containers
All service are separate repo and contains docker file to build the image
Only nginx 80/443 needs to be exposed to outside world
All other communication happens between nginx and other 4 services
On single node it utilizes docker-compose installed
All services are part of docker-compose.yaml
For the app, ONDC is publishing all images to public docker repository and using docker-compose-with-images.yaml to deploy all services
How to build a image
Go to directory containing the dockerfile
Run following to build the image
docker build -t ondc/ondc-python-protocol-layer:pr-sse-v7.1.1
All environment variables are kept in .env file
A local .env file must be present in same folder as docker-compose.yaml
Sample env file (without any creds) - https://github.com/ONDC-Official/ondc-sdk/blob/main/.env-local
Prerequisites
For the white label app, ONDC has used ansible to deploy and generate ssl certificates
The public key of the node to generate ssl and make it available for the seller apps to identify the buyer app
Docker and docker compose needs to be installed
Access to github repository to clone
Create a copy of .env-local with valid credentials and name it .env-<stagename>. E.g. .env-prod
Using ansible
We’re using Ansible for installing all the services and to generate an SSL certificate. To use ansible scripts for deployment, please use the following commands:
ansible-playbook -i ansible_hosts buyer-app-install-for-ssl.yaml
It will ask for three parameters,
    Hostname - Needs to be mentioned in the hostname file
    Domain To Host - E.g. http://buyer-app.ondc.org
    Stage Name - Used for copying the .env file, e.g. if an env file .env-prod is created, then the value should be “-prod”
For HTTPS deployment:
The above process will allow you to deploy the application and have an SSL certificate generated, but the NGINX server will not be listening for requests on the 443 port. To enable it to listen to 443, you have to run another ansible file that has the right NGINX configuration picked from the repo. This way, it is a 2-step process, where we do the above listed process for deployment and then run another script on top of that to finish for SSL.
For running the second file, you can use the following commands:
ansible-playbook -i ansible_hosts buyer-app-run.yaml
It will again be asking for three parameters, please make sure to use the same one’s as before,
Hostname - Needs to be mentioned in the hostname file
Domain To Host - E.g. http://buyer-app.ondc.org
Stage Name - Used for copying the .env file, e.g. if an env file .env-prod is created, then the value should be “-prod”

CHAPTER 3 - APIs
search
Buyer NP sends /search request for higher level category (Grocery, F&B, etc.) to gateway to broadcast to all Seller NPs that have catalogs for that category
Seller NPs respond, by sending catalogs, using /on_search callback, which is then processed and displayed to buyer

select
/select: request quote & availability for items by passing the items in the request payload directly to the Seller NP
/on_select: Seller NP responds with a quote for selected items, their availability, offers applicable, etc.

init
/init: initiate checkout process by providing delivery address, contact information and by agreeing to the Seller NP terms & conditions
/on_init: seller responds with the final quote for the cart, after agreeing to the buyer NP terms & conditions

confirm
/confirm: place order on the seller after selecting payment option (prepaid, cash-on-delivery) and making payment for prepaid
/on_confirm: seller NP responds and either auto-accepts the order or forwards to seller for acceptance
/confirm & on_confirm constitute the digital contract between the buyer NP and seller NP for the order
After the order is placed, the fulfillment will be completed by the seller, which will provide interim status updates for the buyer

status
/status: buyer or buyer NP can request current status for the order
/on_status: seller can send the current status, either in response to /status or can push updates on status change until the terminal state
track
Used for real-time tracking of hyperlocal orders or interim states for inter-city orders
IGM
Used for communicating tickets raised by buyer to the corresponding seller for resolution
API
Description
/issue
Complainant sends ticket using /issue, with expected time for response & resolution
/on_issue
Respondent responds to ticket sent, with status update
/issue_status
Complainant requests current status of ticket
/on_issue_status
Respondent provides status update for ticket, either in response to request by complainant or as push updates until resolution

CHAPTER 4 - Becoming a Buyer NP
Any entity that wants to be live on ONDC has to go through the following stages for onboarding. The Network Integration Guide gives details on each of these steps:
Staging: develop buyer app, test API flows
Pre-Production: integration testing with other seller NPs in a production-like environment (i.e. all integration flows, but without transfer of money or movement of goods), verification of production readiness by ensuring compliance to policy, operations and tech requirements
Production: transact with other NPs, with transfer of money and movement of goods
Network Policy Requirements
ONDC policy requirements define how NPs will legally behave and operate on the network. In any individual sale, the Buyer and Seller are bound by the terms of the sale, and the title for the goods is transferred from Seller to Buyer through the invoice. The Buyer has a pre-existing legal relationship with the Buyer App (through the Buyer App’s terms & conditions), and the Seller has a pre-existing relationship with the Seller App (through the Seller App’s merchant agreement, or terms & conditions). There is no direct legal relationship between a Buyer and Seller App, or Seller and Buyer App.
Complete ONDC network policies can be found here.
NPs have to sign a Network Participant Agreement, which signifies that the NP has given assent to all ONDC network policy requirements.
Network Operations Requirements
ONDC operations team shall check if the app has implemented the necessary compliances from a business operations perspective. The requirements have been detailed out in the "Instructions for Ops Readiness".
Technical Requirements
ONDC technology team shall check if the app has complied with API specs as per the contract document.
